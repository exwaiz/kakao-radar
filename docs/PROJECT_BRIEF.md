# 카톡 요약 서비스 — 프로젝트 브리프

2026-09-18 사용자 변경: 오늘만 한국 시간 30분마다 Telegram 요약, 실제 근거 대사 인용 추가. 9/19 자정에 23:00/하루 1회 자동 복귀. AI 하루 $1은 유지하고 인용은 이후에도 유지한다. 인용은 같은 기기/방의 live 원문에서 그대로 발췌하며 local 영구 quote 사본은 만들지 않는다.

작성일: 2026-09-16 · 갱신: 2026-09-17 · 상태: Android 0.3.1 / 서버 0.6.0 WSL 통합, 실제 업로드·OpenAI·Telegram API 검증 · 임시명: kakao-radar

최신 사용자 결정: M1은 실제 방 선택·메시지 저장을 기준으로 잠정 성공으로 보고 제목 parser 보완은 후속으로 미룬다. 서버는 현재 노트북의 WSL이며 OpenAI 하루 비용 상한은 $1, 관심사는 삼성전자·반도체·산업 흐름·회사 분위기·재미/공감 반응·중요 정보·gossip·부동산이다. 기존 Telegram 개인 봇 채팅으로 한국 시간 23:00에 하루 1회 요약한다. 긴급 발송은 기본 꺼짐이다. 실제 폰 350건 업로드 및 Telegram 설정 검증 요약 API 수락을 확인했다. 수집률, 50주제 품질 평가, 본폰 화면 표시와 야간 운영은 별도 검증이다. 현재 운영 계약은 [WSL_RUNTIME.md](WSL_RUNTIME.md), [M5_LATENCY.md](M5_LATENCY.md)가 아래 과거 제안보다 우선한다.

## 1. 원본과 해석 기준

원본: ChatGPT 「카톡 요약 서비스 설계」, 대화 ID `6aaa7f42-bb2c-83e8-820a-8e2e18367add`. 최초 서비스 설계 요청과 Codex로 작업을 이어가는 방법에 대한 질문을 포함한 전체 2개 턴을 검토했다. 이 문서는 원문 전체의 복사본이 아니라 개발을 위한 분석 결과다.

진행 이력: 세 설계 문서 작성 후 Android 알림 수집·로컬 저장·진단 앱을 구현했다. 2026-09-16 실기기 첫 사용에서 KakaoTalk callback 자체는 들어오지만 현재 `MessagingStyle` 전용 parser가 모든 관찰 callback을 `unsupported_kakao_callbacks`로 분류하는 현상을 확인했다. 따라서 M1은 "수집률 측정" 이전 단계인 **실제 notification format 및 room identity 검증**으로 되돌아갔다. 상세는 `DEBUG_NOTES.md`를 따른다.

## 2. 사용자에게 확인된 문제와 목표

- 참여자가 1,300명 이상인 오픈채팅방의 흐름을 업무·여가·수면 중 계속 따라가기 어렵다.
- 유용한 정보가 있어 방을 완전히 떠나고 싶지는 않다.
- 현재 본폰 대신 서브폰에서 참여하고 가끔 확인하지만, 메시지가 수천 개씩 쌓이면 읽기 어렵다.
- 내용을 자동으로 저장하고 AI로 요약하여 자신에게 필요한 정보만 알림으로 받고 싶다.
- 배터리 부담과 읽는 시간을 줄이는 것이 중요하다.
- 후속 대화에서 수집용 서브폰을 Xiaomi Redmi Note 14 5G / HyperOS 2.0.5 / Android 15로 확인했다. 사용자 제공 정보이며 기기에 직접 접속해 검증한 결과는 아니다.

성공한 사용 경험: 사용자가 오랜 시간 방을 읽지 않아도 짧은 요약으로 관심 있는 주제를 파악하고, 필요한 경우 관련 링크와 근거를 확인할 수 있다.

## 3. 제안된 방향과 미확정 사항

| 항목 | 현재 상태 | 설계 제안 |
|---|---|---|
| 수집 단말 | 사용자 확인: Redmi Note 14 5G, HyperOS 2.0.5, Android 15 | 해당 실기기에서 알림 기반 수집·절전·재부팅 복구 검증 |
| 수집 방식 | 이전 답변의 제안 | 알림 도착 시 로컬 저장, 서버에는 묶어서 업로드 |
| 기술 구성 | 구현·합성 검증 | Kotlin·Room·WorkManager, FastAPI·PostgreSQL·Python Worker |
| 분석 방식 | M3 기준선 구현, 사용자 품질 미검증 | 규칙 전처리 → 주제 묶기 → 관심도 분류·근거 요약 |
| AI 공급자·모델 | 미확정 | 교체 가능한 서버 모듈로 설계, 비용은 표본 측정 후 결정 |
| 알림 채널 | ntfy 어댑터 선행 구현, 운영 선택/연결 미확정 | MVP는 기존 채널 하나, 전용 앱·FCM은 후속 후보 |
| 분석 주기 | 미확정 | 서버 미처리 수집 건수 500개 또는 마지막 처리 후 3시간을 초기 실험값으로 사용 |
| 관심 프로필 | 미확정 | 사용자가 관심·제외 주제와 좋은 알림 예시를 지정 |
| 보관 기간 | 미확정 | 원문 7일, 요약 90일을 검토용 기본값으로 제안 |
| 실행 환경·예산 | 미확정 | 단일 서버로 시작, 월 운영비·AI 일일 상한을 정한 뒤 연결 |

이전 답변의 AI·개발도구·금융·중국 등 관심사 목록, importance 90점, 정해진 알림 시간표는 사용자 선택이 아니다. 기기·운영체제와 예산을 추정해서 확정하지 않는다.

## 4. MVP 범위

| 구분 | 포함할 내용 |
|---|---|
| 대상 | 개인 사용자 1명, 명시적으로 선택한 오픈채팅방 1개 |
| 수집 | 알림에 노출된 텍스트·발신자·시각·URL, 미디어는 유형 표시만 |
| 신뢰성 | 로컬 큐, 재시도, 중복 처리, 수집·업로드 상태 표시 |
| 분석 | 명백한 잡담의 후보 제외, 주제 단위 관심도 판단과 근거가 있는 요약 |
| 전달 | 정기 요약, 중복 알림 억제, 조용한 시간, 채널 하나 |
| 피드백 | 유용함·관심 없음 기록, 우선 수동 프로필 조정에 활용 |
| 관찰 | 마지막 수집·동기화 시각, 큐 잔량, 파싱 실패, AI 사용량 |

초기 범위 밖: 과거 전체 메시지 복구, 100% 아카이브 보장, 사진·음성·파일 본문 분석, 카톡에 자동 답장, 접근성 UI 자동화, OCR, 비공식 DB 추출, 다른 서비스 수집, 공개 배포·다중 사용자, 자동 학습 시스템.

긴급 알림은 목표 경험의 확장으로 남긴다. 정기 배치만 처리하면서 초 단위 즉시 전달을 약속하지 않는다.

## 5. 검토용 품질 기준

아래 값은 사용자와 검토할 초기 기준이며 측정 결과가 아니다.

| 지표 | 측정 방법 | 제안된 통과 기준 |
|---|---|---|
| 텍스트 수집률 | 실제 방의 대조 가능한 표본 메시지 중 정확히 수집한 비율 | 총 표본 500건 이상에서 95% 이상, 상태별 결과 별도 보고 |
| 중복률 | 저장 메시지 중 확인된 불필요한 중복 비율 | 1% 이하 |
| 정상 반복 보존 | 같은 사람이 같은 짧은 문장을 반복한 통제 시나리오 | 서로 다른 메시지를 잘못 합친 사례 0건 |
| 방 구분 | 동일·유사 제목 방과 다른 앱 알림으로 검증 | 미허용 방 업로드 0건 |
| URL 보존 | 대조 표본의 텍스트 URL 중 정확히 보존한 비율 | 99% 이상 |
| 오프라인 복구 | 네트워크 차단 후 재연결, 전송 도중 프로세스 중단 | 로컬 저장 완료된 이벤트의 누락·재전송 중복 0건 |
| 요약 근거 | 표본 요약의 각 핵심 문장과 근거 메시지 대조 | 근거 없는 핵심 주장 0건 |
| 개인화 품질 | 사용자가 표본 50개 주제에 관심 여부 표시 | 관심 주제 재현율 90% 이상, 알림 후보 정밀도 80% 이상 |
| 배터리·지연·비용 | 유사 사용 조건의 수집 전후 비교 및 구간별 시간·사용량 기록 | 측정 후 사용자 허용치를 정함; 현재 숫자 보장 없음 |

수집률 분모는 실제 메시지 대조 표본이다. 알림 콜백 개수나 읽지 않은 메시지 배지만으로 수집률을 계산하지 않는다. 대조 원문 확보가 불가능하면 ‘전체 수집률 미검증’으로 남기며 통과로 처리하지 않는다. 삭제·이미지 등 범위 밖 항목은 별도 집계해 제외 범위를 드러낸다.

## 6. 마일스톤과 판단 지점

사용자는 폰을 조작할 수 없는 동안 대상 방이 발견됐다고 가정한 다음 단계 개발을 승인했다. 이에 M2를 합성 데이터로 구현했고 최신 M2 커밋에서 M3 선행 구현도 명시적으로 요청했다. 아래는 순서와 완료 기준이며 M1의 실제 수집률 통과나 운영 환경 완료를 선언하지 않는다.

| 단계 | 작업과 산출물 | 완료 기준·다음 단계 조건 |
|---|---|---|
| M0 — 설계 검토 | 세 설계 문서와 수집 단말 확인 완료, 후속 구현 요청 수신 | 완료; M1 진행 |
| M1 — 수집 가능성 검증 | Android 수집·방 선택·진단 | **사용자 잠정 성공 인정.** 실메시지 저장. 제목 parser·수집률·야간/재부팅 실측은 후속 |
| M2 — 안정적 저장·동기화 | Room 큐 → 로컬 HTTPS → WSL PostgreSQL | **실연결 확인.** 서버 350건, 폰 sent 350/pending 0. 절전/USB 재연결·재부팅 장기 운영은 후속 |
| M3 — 관심도·요약 평가 | OpenAI, 확정 관심사, 근거 검증·일일 $1 예산 | **실제 분석 작동.** 주제 누락·불확실성·근거 출력 보강. 사용자 50주제 품질 평가는 남음 |
| M4 — 본폰 전달 MVP | Telegram 23:00, 하루 1회·중복 억제·피드백 | **실제 API 수락 확인.** 검증 요약 1건 발송. 본폰 표시/열람·다음 정기 발송·외부 웹 근거 링크는 후속 |
| M5 — 지연 개선·긴급 알림 | p50/p95·첫 열람·urgent threshold/cooldown | **구현·통합 테스트 완료.** urgent 꺼짐. 단말 표시 지연·실환경 5분 목표 통과는 별도 |

M1은 운영 품질 판단 지점이다. 이번 사용자 지시로 M2 합성 개발은 먼저 진행했으며, 실제 수집 부족은 별도로 해결해야 한다. 수동 대화 내보내기 기반 요약처럼 달성 가능한 범위를 검토하되, 지원 여부를 확인하고 사용자와 방향을 정한다. 접근성 수집으로 자동 전환하지 않는다.

## 7. 검토할 선택 사항

서브폰 기종·OS·버전은 확인됐고 후속 구현이 요청됐다. 현재 필요한 다음 검증은 수집 앱 설치 후 실제 방의 알림 형식·수집률 확인이다. 본폰 OS는 알림 채널 선택 전에 확인하며, M1의 로컬 수집 검증을 막는 조건은 아니다. 실제 방 선택은 단말 앱에서 수행한다.

M2/M3/M4 선행 개발은 localhost와 합성 데이터를 사용한다. 실제 운영 전 서버 실행 위치·HTTPS와 보관 기간을 확인한다. M3 프로필 활성화와 외부 AI 연결 전에 관심 주제·제외 주제·좋은 알림 예시와 AI 예산을 정한다. M4 실제 발송 전에 본폰 채널·알림 허용 시간·일일 상한을 정한다. M5 전에 ‘긴급’의 정의와 허용 지연을 정한다.
